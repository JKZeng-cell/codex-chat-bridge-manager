# v1.0.7 - Reply Delivery Repair / 回复修复

## 中文

- 修复 Codex 已发出 `turn.completed` 且答案已生成，平台任务却一直等待
  CLI/MCP 退出、最终被误报为十分钟超时的问题。只在回合确实结束后进行
  有界收尾；没有完成事件的任务仍受原超时约束，不把中间消息当成完成。
- 钉钉采用官方当前 AI 卡片模板，补齐正文显示顺序、自动布局及
  INPUTING → FINISHED 状态。检查 HTTP 200 中的业务投递失败，并回退文本；
  流式结束失败时仍尝试提交完整正文和最终状态。
- 企业微信增加等待反馈，提前结束临近过期或更新次数过多的流式窗口，
  任务完成后用独立消息发送完整结果。回执等待有界，超长正文不丢弃。
- 慢速接收确认不再阻塞 Codex 开始执行；工作台区分答案生成与实际投递，
  未送达时保留本地结果并显示提示。重复连接状态不再淹没错误日志。
- 不修改全局 Codex/MCP 配置，不重新发送旧任务，不更改机器人或 CLI 授权。

全局 MCP 授权或网络故障仍可能拖慢模型初始化；等待反馈不等于初始化提速。
平台接口模拟测试不等于真实手机端显示验收，需要发送新消息确认。

## English

- Completed Codex turns no longer wait indefinitely for CLI/MCP teardown and
  become false ten-minute timeouts. Cleanup is bounded after a terminal turn;
  partial agent messages alone never count as successful completion.
- DingTalk uses the current official AI card template, explicit content order,
  auto-layout and INPUTING/FINISHED transitions. Business failures inside HTTP
  200 responses trigger text fallback. Final card data is committed even when
  the streaming finalizer fails.
- WeCom sends waiting feedback and switches aging or over-updated streams to
  independent final delivery. Acknowledgement waits are bounded and long
  responses are preserved.
- Slow receipt delivery no longer blocks execution. The workbench distinguishes
  generated results from successful delivery; repeated connection states no
  longer hide errors in the recent log.
- No global Codex/MCP changes, replay of old requests or authorization resets.
  Existing MCP/network failures may still delay initialization. Mock transport
  tests are not proof of live mobile-client rendering.
